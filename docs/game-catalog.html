Token Games · design note · task 480

A game catalog that lives on GitHub

Anyone can write a Token Games overlay game. Everyone else finds it in a list inside the app, presses Install, and picks it in Settings to see it in the notch or in a pop-out window. This page shows the experience, the GitHub plumbing under it, and how to keep third-party code from hurting anyone.

  1. Browse
  2. Install
  3. Pick
  4. Play in the notch

The short answer

  • Catalog: a public registry repo where each game is one small pointer file added by pull request. CI turns the pointers into a signed index.json.
  • Downloads: each game ships as a zipped web bundle on its own GitHub Release, pinned by commit and sha256. No executables.
  • Running: every game runs in its own sandboxed Electron view with a tiny API: token counts, its own settings and save data, and window size. Nothing else.

3 · Install and run mechanics in Electron

A game is a web bundle, run in a box with a narrow door

The shell stays the only thing with real powers. A game is HTML, JS and assets. It draws on a canvas and listens for token events. Anything that needs the operating system goes through the shell.

What a game contains

  • game.json, an index.html entry, scripts, images, audio.
  • No Node code, no native modules, no installers.
  • The shell loads it from tgame://<id>/, a custom protocol that serves only that game's folder (with a path traversal check).
  • Heavy simulation can use a Web Worker or WebAssembly. The Ant Farm's chunked world already fits this.

The brief mentioned a small main-process entry. I recommend not allowing one. Main-process code can do anything the user can. Everything a game legitimately needs (window, feed, save) is already provided by the shell.

How it is loaded

  • One WebContentsView per visible game (BrowserView is deprecated; the repo's Electron 38 has the newer class).
  • Own session persist:game-<id>: separate storage, cookies and permission handler. All permission requests (camera, mic, geolocation, notifications) are denied.
  • Headers add a strict CSP: default-src 'self'; connect-src 'none', or a list of hosts the player approved.
  • Navigation and window.open are blocked, as the Ant Farm window already does.
preload.ts (the whole API a game sees)
contextBridge.exposeInMainWorld('tokenGame', {
  api: 1,
  manifest: { id, version },
  // token counts and timestamps, never content
  onEvent(fn: (e: UsageEvent) => void): () => void,
  // 'mini' strip, 'expanded' drop-down, or 'window'
  scale: { get(): Scale, onChange(fn): () => void },
  settings: { get(): Promise<object>, set(patch): Promise<object> },
  save: { load(): Promise<unknown>, save(data): Promise<boolean> }, // capped
  requestPopOut(): void,
  requestDock(): void,
  reportStatus(s: { headline: string }): void, // shown in the notch
})

Versioning and updates

  • Semver per game, plus minShell and an integer api version. A game that needs a newer shell shows "Needs Token Games 0.4" and cannot be installed.
  • The shell checks the index at launch and every 6 hours. Updates install side by side, then the active pointer switches. The old version is kept for one rollback.
  • If an update asks for new permissions, it is not applied until the player approves. Same permissions can update quietly if the player turns that on.
  • Saves live outside the version folder, so an update keeps your colony.

Offline, uninstall, several at once

  • Offline: installed games run without network. Browse shows the cached list with an "offline" banner; Install is disabled until the index loads.
  • Uninstall: deletes the version folders and clears the game's session. The player chooses to keep or delete the save.
  • Several games: every active game gets its own view. Cap at three running. Hidden games do not draw. Events fan out to each one, and each gets a frame budget.
  • Developers: "Add local folder" in Settings loads an unpacked game with a visible "Local" badge, the same path phase 1 uses.
4 · Security and trust

Third-party code, with five layers that each assume the one before failed

A game is code written by a stranger that runs on your Mac, near your editor. The goal is that the worst a game can do is draw badly or burn some CPU. It must not be able to read your transcripts, your files or your keys.

Built-in no prompt

Ships inside the app. Ant Farm today. Reviewed with the shell, updated with the shell.

Verified ✓ badge

A maintainer read the code at a pinned commit. Updates are re-reviewed from a diff. Shown first and installable in one click after the permission sheet.

Community warning

CI passed, nobody read it closely. Hidden until the player turns on "Show community games". The sheet says so plainly.

Local developer

An unpacked folder added in Settings. No registry, no hash. Marked "Local" everywhere.

What the shell must never allow

  • Reading Claude Code transcripts or any file. The shell's feed reader turns lines into counts and drops the text, as it does now.
  • Prompts, code, file names, project names or session paths in the feed. Counts, model name and time only.
  • Node, require, remote modules, eval from remote code, or loading scripts from another site.
  • Any network by default. A game may list hosts; the player approves them and the CSP enforces them.
  • Reading keychain items, environment variables, clipboard, screen, camera, microphone.
  • Stealing keyboard focus, or drawing outside its own view. The shell draws the title bar and the game name so a game cannot fake a system dialog.
  • Main-process code from a game.

Supply chain and review

  • Pin everything. The registry stores the commit hash and the zip's sha256. CI rebuilds the zip from that commit and compares hashes, so the reviewed source is the shipped code.
  • Sign the index. Maintainers sign index.json with an ed25519 key (minisign style). The public key is compiled into the app. A hijacked Pages site cannot add games.
  • Revoke. blocklist.json in the signed index disables an id or a hash on the next launch, even if installed.
  • Block downgrades to versions older than the one installed, so an old vulnerable build cannot be replayed.
  • Update review. Verified updates trigger a diff for a maintainer; new permissions always do.

Executables, Gatekeeper and notarisation

If downloads contained binaries, macOS would need them to be Developer ID signed and notarised, and every game would become a native-code review. Avoid that by design: CI rejects any file with an executable bit or Mach-O, ELF, PE or .node magic bytes. The shell itself is the only thing that is signed and notarised, once per release. Because games are plain files read by an already-trusted app, Gatekeeper never sees them.

Remaining risk, stated plainly: a sandboxed page can still waste battery, show an ugly or misleading picture, and a Chromium sandbox escape is possible in theory. Frame budgets, a "pause game" kill switch in the island and a fast Electron update habit cover most of it. Human review is the only defence against a cleverly obfuscated game, which is why the verified tier exists.

5 · The Cursor and MCP angle

One thin CLI, an MCP server on top, and Momo can use both

Think of how Cursor or Claude Code installs an MCP server or plugin: you ask, it lists, you approve. Games can work the same way. The key is that the app, the CLI and the MCP server all call the same installer, so the rules (checksums, permission sheet) cannot be bypassed by whichever door you use.

Guardrails that matter

  • The agent can ask, not approve. Permission sheets only appear in the app.
  • Game names and descriptions come from strangers. The MCP server returns them as data fields, truncated and stripped of markup, so a game cannot talk the agent into doing something.
  • The local socket accepts only the same user and is off until the app is running.
  • Momo can read game_status for something to say, for example mentioning that the colony is hungry after a quiet day.
6 · Contributing flow for other people

From template to everyone's catalog in six steps

The author's commands

npm create token-game@latest my-game
cd my-game
tokengames dev        # sandbox preview, fake feed slider
tokengames check      # manifest, size, files, smoke test
git tag v0.1.0 && git push --tags   # Action builds the Release zip
# then open a PR to the registry adding games/my-game.json

tokengames dev runs the game exactly as the app would, including the missing Node and the CSP, so what works there works for players.

What CI checks on every submission

  • Manifest matches the schema; id is unique and lowercase
  • Version is higher than any listed version
  • Bundle under 10 MB; files only from an allowlist of types
  • No executable bit, no Mach-O, ELF, PE or .node files
  • No remote script tags, no eval of fetched text
  • Zip rebuilt from the pinned commit has the same sha256
  • Screenshots, icon and licence present
  • Headless smoke test: 10 s with a synthetic feed at all three sizes, draws a non-blank frame, stays inside the frame budget, makes no network request
  • Requested permissions are listed in the PR description

Updates use the same route: a PR that changes tag and commit. Later, a bot can auto-merge updates from verified authors when CI is green and permissions are unchanged.

Risks

  • Sandbox gaps. A game that needs something the API lacks. Keep the API small and add on demand, versioned by api.
  • Performance. Three canvases at once on a laptop. Frame budgets, hidden games stop drawing, a hard cap.
  • Review load. One person reading every PR does not scale. Verified tier only on request; community tier is automated.
  • Key custody. The signing key must live in a protected CI secret or a hardware key, with a documented rotation plan.
  • API churn. Task 479 is still shaping the shell. Lock the manifest and tokenGame API before phase 2 ships.
  • Private repo. The registry and games must be public.
  • GitHub dependence. Rate limits or outages. Cache the index and keep a mirror option.

Decisions for Jake

  • Create a public token-games-registry repo and pick the maintainers.
  • Confirm: no main-process code in third-party games.
  • Community games off by default: yes or no.
  • One game at a time first, or several from the start?
  • Who holds the signing key?

Recommendation

  1. Build phase 1 first. It is cheap, it forces the manifest and the sandbox API to be real, and it gives you the Settings picker with the games you already have.
  2. Use a curated public registry (pull requests, CI, signed index.json) with GitHub Releases as the download. Skip git checkouts and npm. Add topic search only later, as an opt-in tier.
  3. Keep games to sandboxed web bundles with a counts-only API, add the CLI and MCP in phase 3, and open the doors to strangers (phase 4) only when CI can rebuild and smoke-test every submission.
